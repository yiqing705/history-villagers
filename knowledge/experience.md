# 開發經驗

這裡記錄可在後續功能中重用的設計與實作經驗。每筆經驗應附上適用範圍，避免把原型階段的假設直接當成正式產品規則。

## 2026-11-19：把答題內容與互動邏輯分開

### 做法與觀察

- 首頁原本將每個答案的回應直接寫在點擊事件邏輯中；改成一份題目物件後，正解、選項迷思、解題說明與答對延伸都能清楚檢視和替換。
- 錯答回饋依玩家實際選項指出迷思，再交代考點和正解，較能體現「教會怎麼想」，而不是只回報答錯。
- 對同一題先用結構化物件呈現，可快速驗證內容欄位是否足以支援 UI；正式擴充題庫時再改由 JSON 或其他資料來源載入。
- `knowledge/question-format.md` 是格式說明；示範題仍需學科審核，不能因互動可用就視為內容已驗證。

### 未來可使用的範圍

- 新增任何學科、居民或單題互動時，沿用 `id / subject / source / scope / keyPoint / stem / options / answer / distractors / solution / extension` 欄位。
- 同一套回饋流程可供歷史、十五篇古文及自然科學題目共用，再由題目資料調整說明文字。
- 題目開始進入批量維護、篩選或審稿階段時，將題目物件搬至獨立 JSON，並加上格式驗證；避免讓首頁程式檔變成題庫。
- 正式加入歷屆試題或對外教學內容時，增加來源與授權檢查、領域審稿和範圍校對；本原型尚未涵蓋這些流程。

## 2026-11-19：把歷史人物造型依據與創作設定分開

### 做法與觀察

- 居民檔案分開記錄可查證的生平／作品、館藏肖像來源、Q 版造型提案和虛構對話，可降低把後世畫像誤認成寫實肖像、把遊戲台詞誤認為史料原文的風險。
- 蘇軾的示範參考一件典藏畫像資料中記錄的紗冠、白袍與竹杖等圖像特徵；因為館藏畫像仍是後世藝術詮釋，角色資料會說明限制，而不宣稱還原本人真實長相。
- 原型階段先保存來源連結及圖像授權提醒，未下載或重用典藏圖像。

### 未來可使用的範圍

- 歷史人物、十五篇古文作者／人物及自然科學人物的所有居民檔案，都沿用 `knowledge/resident-profile-format.md`，並為每一項學習事實與視覺線索留下來源。
- 美術製作前先整理可辨識的服飾、肖像、文物或科學相關物件，再做風格化 Q 版設計；若沒有可靠個人外貌資料，改用時代或貢獻符號，避免假造細節。
- 發布館藏圖片、原文或引文前，先確認該素材本身的授權條件與標示要求；連到公開網頁不代表素材可任意重製。
- 角色對白、陪伴問候及想像情境要標為創作內容；直接引用古文或人物文句時另外校勘來源與上下文。

## 2026-11-19：用原創 SVG 提案落地 Q 版辨識元素

### 做法與觀察

- 將紗冠、白袍、竹杖等有館藏說明脈絡的元素，畫成原創 SVG 小頭像；以幾何圖形完成概念，不直接複製館藏畫作，縮放時也能保持清晰。
- 問候卡、題目卡和頁首小頭像共用同一張角色圖，讓同一居民在不同介面保持視覺連貫。
- SVG 旁附替代文字，提供造型和身份提示；正式美術仍須由審核流程確認辨識度、比例和可讀性。

### 未來可使用的範圍

- 為其他歷史、古文與科學居民製作小尺寸、可縮放的向量頭像時，先用原創 SVG 驗證輪廓、服裝與象徵物，再決定是否投入完整立繪和動畫。
- 每張角色圖都對應人物檔案中的視覺來源，替代文字要描述角色身份及必要的圖像脈絡，並檢查小尺寸對比。
- 若後續採用館藏圖片或委外插畫，改用明確的授權、署名和素材管理流程；原型 SVG 的作法不代表第三方圖片可直接使用。

## 2026-11-19：提供可略過且不留存的近況問候

### 做法與觀察

- 把「分享心情」、「先聽居民說話」和「略過近況」都做成明確選項；居民只更新當頁對話，不要求玩家解釋或完成任務。
- 以按鈕與 `aria-live` 更新回覆，讓選項可鍵盤操作並讓輔助科技讀到新的居民回應。
- 網頁展示原型不寫入儲存空間；因此重整後不會保留玩家近況。這是目前原型的隱私預設，不代表正式產品的玩家記憶規則已決定。

### 未來可使用的範圍

- 適用於情緒近況、日常閒聊、個人化關懷等非必要對話；每個分享情境都要能不回答並繼續遊戲。
- 若正式遊戲需要跨日記住玩家分享，先定義明確同意、保存期限、查看／修改／刪除方式，以及未分享時的等價體驗，再實作持久化。
- 開發網頁互動時，使用原生按鈕及 `aria-live` 回報動態內容，可同時改善鍵盤操作與螢幕閱讀器支援；上線前仍需實機無障礙檢查。

## 2026-11-19：分清遊戲日與現實日

### 做法與觀察

- 對照最初需求後，發現「遊戲一天約 30 分鐘」被路線圖誤改寫成「題目按現實日更新一次」。修正後恢復為每個遊戲日都可有居民提問，時間尺度不再互相矛盾。
- 將玩家錯過問題後仍可補做、重做，寫成時間設計原則，避免半小時輪替變成登入壓力或內容損失。
- 計時器和輪替尚未實作；只有把需求和推薦規則寫清楚，不代表功能已完成。

### 未來可使用的範圍

- 適用於所有使用真實時間切換的遊戲日、活動與每日任務；文件中應明確說明每一單位是「遊戲時間」還是「現實時間」。
- 若採半小時遊戲日，輪替事件與題目發放分離：到期新增新題，但舊題仍留在筆記，可補做或重練。
- 實作時應以本地時鐘、不同時區、關閉分頁、重新整理和跨邊界的情況驗證；在題庫與事件存取模型成熟前，不急著加倒數計時 UI。
