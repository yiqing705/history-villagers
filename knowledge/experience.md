# 開發經驗

這裡記錄可在後續功能中重用的設計與實作經驗。每筆經驗應附上適用範圍，避免把原型階段的假設直接當成正式產品規則。

## 2026-11-19：把答題內容與互動邏輯分開

### 做法與觀察

- 首頁原本將每個答案的回應直接寫在點擊事件邏輯中；改成一份題目物件後，正解、選項迷思、解題說明與答對延伸都能清楚檢視和替換。
- 錯答回饋依玩家實際選項指出迷思，再交代考點和正解，較能體現「教會怎麼想」，而不是只回報答錯。
- 對同一題先用結構化物件呈現，可快速驗證內容欄位是否足以支援 UI；正式擴充題庫時再改由 JSON 或其他資料來源載入。
- `knowledge/question-format.md` 是格式說明；示範題仍需學科審核，不能因互動可用就視為內容已驗證。

### 未來可使用的範圍

- 新增任何學科、居民或單題互動時，沿用 `id / subject / source / scope / keyPoint / stem / options / answer / distractors / solution / extension` 欄位。
- 同一套回饋流程可供歷史、十五篇古文及自然科學題目共用，再由題目資料調整說明文字。
- 題目開始進入批量維護、篩選或審稿階段時，將題目物件搬至獨立 JSON，並加上格式驗證；避免讓首頁程式檔變成題庫。
- 正式加入歷屆試題或對外教學內容時，增加來源與授權檢查、領域審稿和範圍校對；本原型尚未涵蓋這些流程。

## 2026-11-19：把歷史人物造型依據與創作設定分開

### 做法與觀察

- 居民檔案分開記錄可查證的生平／作品、館藏肖像來源、Q 版造型提案和虛構對話，可降低把後世畫像誤認成寫實肖像、把遊戲台詞誤認為史料原文的風險。
- 蘇軾的示範參考一件典藏畫像資料中記錄的紗冠、白袍與竹杖等圖像特徵；因為館藏畫像仍是後世藝術詮釋，角色資料會說明限制，而不宣稱還原本人真實長相。
- 原型階段先保存來源連結及圖像授權提醒，未下載或重用典藏圖像。

### 未來可使用的範圍

- 歷史人物、十五篇古文作者／人物及自然科學人物的所有居民檔案，都沿用 `knowledge/resident-profile-format.md`，並為每一項學習事實與視覺線索留下來源。
- 美術製作前先整理可辨識的服飾、肖像、文物或科學相關物件，再做風格化 Q 版設計；若沒有可靠個人外貌資料，改用時代或貢獻符號，避免假造細節。
- 發布館藏圖片、原文或引文前，先確認該素材本身的授權條件與標示要求；連到公開網頁不代表素材可任意重製。
- 角色對白、陪伴問候及想像情境要標為創作內容；直接引用古文或人物文句時另外校勘來源與上下文。

## 2026-11-19：用原創 SVG 提案落地 Q 版辨識元素

### 做法與觀察

- 將紗冠、白袍、竹杖等有館藏說明脈絡的元素，畫成原創 SVG 小頭像；以幾何圖形完成概念，不直接複製館藏畫作，縮放時也能保持清晰。
- 問候卡、題目卡和頁首小頭像共用同一張角色圖，讓同一居民在不同介面保持視覺連貫。
- SVG 旁附替代文字，提供造型和身份提示；正式美術仍須由審核流程確認辨識度、比例和可讀性。

### 未來可使用的範圍

- 為其他歷史、古文與科學居民製作小尺寸、可縮放的向量頭像時，先用原創 SVG 驗證輪廓、服裝與象徵物，再決定是否投入完整立繪和動畫。
- 每張角色圖都對應人物檔案中的視覺來源，替代文字要描述角色身份及必要的圖像脈絡，並檢查小尺寸對比。
- 若後續採用館藏圖片或委外插畫，改用明確的授權、署名和素材管理流程；原型 SVG 的作法不代表第三方圖片可直接使用。

## 2026-11-19：提供可略過且不留存的近況問候

### 做法與觀察

- 把「分享心情」、「先聽居民說話」和「略過近況」都做成明確選項；居民只更新當頁對話，不要求玩家解釋或完成任務。
- 以按鈕與 `aria-live` 更新回覆，讓選項可鍵盤操作並讓輔助科技讀到新的居民回應。
- 網頁展示原型不寫入儲存空間；因此重整後不會保留玩家近況。這是目前原型的隱私預設，不代表正式產品的玩家記憶規則已決定。

### 未來可使用的範圍

- 適用於情緒近況、日常閒聊、個人化關懷等非必要對話；每個分享情境都要能不回答並繼續遊戲。
- 若正式遊戲需要跨日記住玩家分享，先定義明確同意、保存期限、查看／修改／刪除方式，以及未分享時的等價體驗，再實作持久化。
- 開發網頁互動時，使用原生按鈕及 `aria-live` 回報動態內容，可同時改善鍵盤操作與螢幕閱讀器支援；上線前仍需實機無障礙檢查。

## 2026-11-19：分清遊戲日與現實日

### 做法與觀察

- 對照最初需求後，發現「遊戲一天約 30 分鐘」被路線圖誤改寫成「題目按現實日更新一次」。修正後恢復為每個遊戲日都可有居民提問，時間尺度不再互相矛盾。
- 將玩家錯過問題後仍可補做、重做，寫成時間設計原則，避免半小時輪替變成登入壓力或內容損失。
- 計時器和輪替尚未實作；只有把需求和推薦規則寫清楚，不代表功能已完成。

### 未來可使用的範圍

- 適用於所有使用真實時間切換的遊戲日、活動與每日任務；文件中應明確說明每一單位是「遊戲時間」還是「現實時間」。
- 若採半小時遊戲日，輪替事件與題目發放分離：到期新增新題，但舊題仍留在筆記，可補做或重練。
- 實作時應以本地時鐘、不同時區、關閉分頁、重新整理和跨邊界的情況驗證；在題庫與事件存取模型成熟前，不急著加倒數計時 UI。

## 2026-11-19：把錯題提示和完整解析分成兩步

### 做法與觀察

- 答錯後先依玩家選項顯示迷思和解題線索，再用明確的「看完整解題思路」按鈕揭露正解。這讓玩家可以先停下來想一次，也保留完整教學回饋。
- 用獨立按鈕而不是把解析藏在 hover 或純色提示中，方便觸控和鍵盤操作；重答會收起解析並清除上一輪狀態。
- 每個錯誤選項都需有自己的回應；資料不完整時不能假裝這是一份有效題目，正式題庫應在發布前驗證選項和解析欄位。

### 未來可使用的範圍

- 適用於單選題、概念診斷及其他先讓玩家自行推理、再展開詳解的學習互動。
- 後續可按年級或題目難度增加第二層提示，但應由玩家選擇何時展開，不強迫連續答錯才可看解析。
- 若介面使用揭露／收合控制，需同步管理按鈕文字、`aria-expanded`、回饋區及重置狀態；加入新互動後一併測試正確、錯誤與重試流程。

## 2026-11-26：讓近況隱私文案符合實際保存行為

### 做法與觀察

- 近況按鈕只更新目前頁面的對話文字，不會保存分享內容；「居民會記得」或「下次再問候」會讓玩家誤以為資料跨次留存，因此改成直接說明只用於當次對話、不會保存。
- 在互動附近交代資料行為，比只在規劃文件註記原型限制更容易讓使用者理解；回答、交給居民說話和略過仍都可繼續，不改變遊戲進度。
- 這項文案說明只適用於目前不持久化的網頁原型，不能當成未來正式遊戲的隱私政策。

### 未來可使用的範圍

- 適用於任何會詢問心情、近況或偏好的原型介面：說明文字必須和實際的記憶、儲存及傳送行為一致，並在互動附近可見。
- 若未來加入跨次記憶或雲端同步，先重新設計告知與資料控制，再更新文案；不可沿用「不會保存」的原型承諾，也不可只改文字而不改實際行為。
- 更新隱私相關功能時，搜尋產品畫面中的「記得」、「下次」等暗示，再逐一比對本機儲存、網路請求及伺服器行為；本次原型沒有後端，仍需在功能擴充時重新檢查。

## 2026-11-26：用免外部引擎依賴的 WebGL 驗證 3D 生活模擬

### 做法與觀察

- 在 GitHub Pages 靜態網站新增獨立散步頁，以原生 WebGL 繪製低多邊形島嶼，避開建置流程和外部遊戲引擎相依；保留既有首頁題目原型，不把它誤當成完整遊戲。
- 把地圖中的人物與商店放在同一組世界座標，玩家以方向鍵／WASD 或觸控方向鈕移動，居民依目標點自行漫步；相機跟隨玩家，互動距離用世界座標判斷。
- 將首頁原型使用的示範題抽到單一共用資料檔，讓 3D 居民對話、答題提示、完整解析、正解及延伸都讀同一份內容，避免兩個介面的答案和文案逐漸不一致。
- 玩家和居民以水平面碰撞半徑互相阻擋，建築和樹幹用矩形障礙物判斷；分開檢查 X 與 Z 軸，使角色碰到居民時可以沿著另一軸滑行，不會整個卡住或穿透角色。
- 將商店、遊戲內橡實與購買回應保留在一般 HTML 控制項，使用 `aria-live` 呈現居民和商店訊息；讓輔助科技可讀到互動回應，並避免把操作綁死在 WebGL 畫布裡。
- WebGL 需要處理 shader 編譯、模型／視圖／投影矩陣和畫布縮放；先支援 WebGL 1 shader 語法，才能避免用 WebGL 2 context 卻送入舊版 shader 而無法啟動。
- 這個原型只驗證移動、簡單碰撞、NPC 漫步、商店及簡單購買；尚無角色動畫、保存資料、正式美術、學習循環或 WebGL 不支援時的 2D 自動降級。

### 未來可使用的範圍

- 適用於想在靜態網站或 GitHub Pages 快速驗證 3D 探索手感的概念原型；如果場景、動畫、碰撞或內容規模快速增加，應重新評估 Three.js、Babylon.js 或 Godot 等引擎與工具鏈，而不是持續擴張手寫 WebGL。
- 適用於將既有問答原型接入新遊戲場景：把題目資料和畫面控制分開，先重用同一題驗證完整學習循環；正式擴充題庫時再加入資料驗證與內容審查，而非複製題目物件到各個畫面。
- 新增場景物件時沿用共用幾何與世界座標，讓移動、居民 AI、碰撞、互動距離及相機更新使用同一個座標系；移動採時間差而非每影格固定距離，避免不同更新率造成速度不一致。
- 適用於小型無旋轉角色的 3D 地圖：圓形碰撞半徑適合居民，軸對齊矩形適合建築；若加入旋轉物件、不同體型或高低差，再改用引擎碰撞體並實際測試邊界案例。
- 互動優先由可聚焦的 HTML 按鈕提供，並以動態文字區回報狀態；觸控方向鈕要支援按住移動及取消事件，鍵盤控制需在視窗失焦時清除按鍵狀態。
- 依目標裝置檢查 WebGL 可用性、畫面比例、耗電與效能；若需要可靠支援舊裝置，另外設計並測試可理解的 2D 降級體驗。

## 2026-11-26：分清學測必修範圍與推薦選文／進階內容

### 做法與觀察

- 以大考中心公布的考科範圍和國家教育研究院課綱作為第一層篩選：學測社會包含必修歷史、地理、公民，自然包含必修物理、化學、生物、地球科學；進階選修內容要另標籤，不能直接寫成全體學測必考範圍。
- 古文學習主題可以連結國語文課綱推薦選文與教材，但推薦篇目不表示一定會出現在某次考題；介面使用「課綱選文」和「自編示範題」等具體標籤，比籠統宣稱「學測必考」準確。
- 居民名單先列領域、候選主題、主要來源與內容限制，並把名單提案和已審核角色分開。這保留了涵蓋各領域的計畫，同時不把候選人物或科學簡化規則誤當作已核准課程。
- 自然科人物主題須附概念界線：孟德爾模式不是所有遺傳性狀的通則；魏格納的大陸漂移證據和現代板塊構造理論需分開表述；伽利略相關逸聞需檢查來源；化學質量關係要寫清楚系統與反應條件。

### 未來可使用的範圍

- 適用於新增任何學測科目或居民時：先用大考中心考科範圍排除偏離的內容，再對照各科課綱的具體學習內容，最後以領域審查確認題幹、答案及解析。
- 製作十五篇古文相關內容時，逐篇連到所採用的推薦選文版本或教材脈絡；若是補充閱讀、進階選修或創作聯想，要獨立標註，不把它們混進必修考試範圍。
- 個別人物的生平來源與學科知識來源應分開保存；館藏資料可支持視覺線索，課綱可界定教學範圍，科學機構可查證概念，但任何單一來源都不會自動替完成的題目背書。

## 2026-11-26：人物提案要分開保存史實、肖像脈絡和遊戲台詞

### 做法與觀察

- 依人物檔案格式先建候選資料，再為每個史實和視覺脈絡連到博物館、教育單位或專業機構來源；找不到可信個人外貌依據時，改用研究物件或作品當原創角色符號，不假裝復原真人長相。
- 來源中的肖像是特定年代、畫家與文化詮釋，不是相機紀錄。由該肖像發展的 Q 版特徵要註明是提案，也不可順手下載或重繪受授權限制的素材。
- 科學人物可自然引出課程概念，但人物故事和概念驗證是兩項不同工作；角色台詞仍標為遊戲創作，人物對學術成就的貢獻要避免過度簡化。

### 未來可使用的範圍

- 適用於新增歷史、文學或科學居民：維持 `verifiedFacts / visualReferences / designBrief / voice / fictionalDialogue / reviewStatus` 分欄，先標 `提案`，經來源和領域審核後再改狀態。
- 為沒有可靠肖像資料的人物設計角色時，可從本人作品、研究工具、時代物件或已知事件抽取圖像線索；每一項仍要標來源和限制，避免由象徵物推演出未證實的個人外貌。
- 需要館藏圖像作造型研究時，記錄館藏項目和圖像年代即可；發布或嵌入原圖前須另外核實授權、署名和重用條件。

## 2026-11-26：用鏡頭投影在 3D 場景上放置居民姓名

### 做法與觀察

- 新增多位居民後，光靠顏色不容易辨認角色；把角色的世界座標經視圖矩陣與投影矩陣轉成畫布座標，再把 HTML 姓名標籤放在對應畫面位置，可讓玩家直接看出島上有誰。
- 姓名標籤跟隨鏡頭與 NPC 漫步更新；位於鏡頭後方或畫面外時隱藏，並以 `aria-hidden` 避免螢幕閱讀器反覆朗讀每一影格移動的標籤，動態對話仍由 `aria-live` 區域播報。
- 角色數量增加時，介面明確標出候選角色和未審核內容；不要把角色名字或一行招呼誤認為完整居民檔案或已審核題庫。

### 未來可使用的範圍

- 適用於 WebGL、Three.js 或其他世界座標場景：為 3D 角色顯示姓名、互動提示或狀態時，透過相機投影定位 2D HTML 層，保留一般 DOM 的可讀性和按鈕操作。
- 加入更遠距離、遮擋、鏡頭縮放或不同裝置畫面比例時，補上深度／可見性判斷、標籤重疊避讓和小螢幕測試；大量 NPC 場景可依角色更新頻率節流標籤投影。
- 對螢幕閱讀器，避免將每影格移動的視覺標籤當成即時語音；改由玩家互動後更新一次有意義的角色名稱與對話狀態。
